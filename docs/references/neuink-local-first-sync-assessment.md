# NeuInk 本地优先、多设备同步评估

日期：2026-11-08。代码基线：`929f504`（本地 beta 与远程 alpha/beta 的共同提交）。

状态：架构研究与建议，尚未实施。不代表功能已经具备，也不代表同意晋级 main。只阅读源码及官方资料，没有读取用户论文正文、密钥或修改资料。后续若确认实施，应将确定的范围纳入开发计划，实际落地后再更新系统架构。

## 结论

适合演进为“本地独立工作 + 可选云同步”，不需要把桌面应用重写成在线应用。阅读、编辑、检索、AI 调用仍在本地；云端提供多设备交换、版本和附件存储。主要工程量在数据一致性和恢复，不在上传文件按钮。

建议首期范围为同一用户的多个桌面设备，排除实时共同编辑、团队权限、网页完整阅读器。保留无需账户的离线使用；同步采用独立开源协议与服务，可连接官方托管或自部署实例，两者使用同一协议。

| 写入口覆盖 | 工程规范以 workspace 为写盘入口，但 `ipc/commands/conversation.rs` 仍直接写对话文件和索引 | 需审计并收拢绕过统一内容提交的路径，否则队列会漏掉变更 |
| UI 本地状态 | reader 列宽等使用 localStorage，恢复草稿有独立存储 | 区分可选用户偏好和设备布局；草稿默认不自动公开同步，远端更新不能覆盖未保存编辑 |

以上是抽样到关键持久化链路的架构评估，不是全仓库所有写点的完整审计。实施第一阶段必须补齐写点和数据格式清单。

## 与 Zotero 的对照

Zotero 将数据同步与附件同步分开；WebDAV 只替代个人库附件存储，不替代条目/笔记的数据同步。其同步 API 使用库/对象版本、条件写、删除日志和本地基线，以增量方式交换内容；不能用“更新时间较新就覆盖”替代这些机制。

- [官方同步说明](https://www.zotero.org/support/sync)
- [官方同步协议](https://www.zotero.org/support/dev/web_api/v3/syncing)
- [条件写与请求幂等](https://www.zotero.org/support/dev/web_api/v3/write_requests)
- [安全与自部署说明](https://www.zotero.org/support/security)

详细出处与许可证调查见 [Zotero 研究](zotero-sync-architecture-research.md)。借鉴协议思想，自行实现 NeuInk 的领域映射；不把 NeuInk 卡片、详略和构思强行塞入 Zotero 条目，也不把 Zotero 云服务当作 NeuInk 的通用存储。

## 建议模块组织

```text
React 阅读/编辑界面
  -> shared/ipc -> 内容操作 -> neuink-workspace（本地内容与恢复事务）
                                   |
                         持久变更记录 / outbox
                                   |
                         neuink-sync（建议新增）
                                   |
                         NeuInk 同步服务（建议新增）
                         /                       \
               元数据、版本、变更流          附件内容存储
```

- `neuink-domain`：同步对象身份与纯合并规则，继续不做网络、文件和 Tauri 工作。
- `neuink-workspace`：本地事务、对象读取/提交、删除记录、远端结果安全应用。已有 JSON/Markdown 可保留。
- `neuink-sync`：游标、基线、上传下载、重试、认证和冲突调度，UI 不承担同步算法。对外仅提供状态、开始/暂停同步、冲突解决等少量接口。
- `neuink-ipc`：向现有全局任务和通知暴露状态，编辑器接到内容变更通知后决定刷新还是保留草稿。
- 同步服务：可独立部署的 Rust 服务；建议初期单实例，PostgreSQL 保存账户/对象/修订/变更日志，附件先落本地持久卷，后续再提供 S3 兼容存储。具体部署依赖需要在实施前核验版本和许可证，不同时支持多种数据库以免扩大测试面。

云端数据库不直接替代客户端工作目录。客户端可新增 SQLite 保存 outbox、基线和同步状态，但它不是简单的可丢弃缓存：删除状态库后必须受控重建基线，不能直接把所有本地文件当成新内容上传。

## 数据分类与首期范围

| 内容 | 策略 |
| --- | --- |
| 条目元信息、标签、归档、笔记、批注、片段笔记 | 首期核心对象，按实体/关系增量同步 |
| 已确认卡片、用户创建卡片、构思及用户确认保存的报告 | 作为用户成果同步，分实体处理；未确认 AI 草稿需单独范围开关 |
| PDF、笔记图片、解析图片 | 附件对象，内容 hash 校验，按需下载、固定离线保留、磁盘配额 |
| 规范化解析结果 | 与文档版本绑定；包含引用依赖的资源清单，跨端保留相同 segment 身份 |
| 已完成译文、逐句重译、详略结果 | 建议可选同步，避免重复花模型费用；区分用户修订与机器生成版本 |
| MinerU 原始 ZIP、可再下载的中间结果 | 默认不传全部；按是否影响重排阅读/来源回溯分类，不能笼统全当缓存 |
| 阅读位置、书签、阅读统计 | 后续同步；位置按设备保留并提供继续阅读，统计按 session/device 去重，不能相加整份累计值 |
| 助手对话 | 后续可选；以 message ID 合并，执行计划、工具授权和未执行 proposal 不在另一端自动恢复执行 |
| 搜索索引、向量库、模型文件、日志、锁、临时文件 | 不同步，设备本地维护/重建 |
| 当前运行中的解析、翻译、AI 任务 | 不同步执行权；不因为收到远端 Running 就启动或重试付费任务 |
| 主题等偏好 | 白名单可选同步；窗口布局/本地路径默认只在本机 |
| API Key、设备令牌、源目录、恢复中的设置草稿 | 排除普通同步；首期新设备自行配置凭据 |

## 必须先定义的协议不变量

1. **保存先于网络**：离线仍可成功保存；内容变更与 outbox 不能分别 best-effort 写入。用 durable journal 记录事务意图，重启可把内容和队列恢复到一致状态。若仅增加“保存后发事件”，崩溃时会漏同步。
2. **可重放**：每项操作有 operation_id，服务端事务内去重。网络超时重试不应创建两份笔记、重复累计统计、重复执行 AI。
3. **版本检查**：library_id/entity_id/base_revision/server_revision/change_cursor/device_id/schema_version；时间用于展示，不能决定因果关系。首次接入给旧对象建立基线，不重写旧 ID。
4. **增量拉取**：服务端变更流分页，客户端原子应用后推进游标；推送时检查 base_revision，不盲目覆盖。拉取应用与用户本地修改发生竞争时要再次校验本地 revision。
5. **来源标记**：远端应用也走统一保存接口，但不能重新生成同一变更上传，避免同步回环。
6. **内容及附件一致性**：附件以 immutable blob/hash 存储，先校验并完成上传，再提交引用；下载未完成时对象显示“附件未下载”，不能误报损坏/删除。PDF 替换必须连同解析版本和批注锚点关系审查，保留历史版本。
7. **删除协议**：软删除、恢复、彻底删除是可同步状态变化。服务端 tombstone 不能因某台清空回收站立即清理；按设备确认水位/保留政策回收，过期游标要求重新拉基线，防止长期离线客户端复活对象。
8. **离线外部编辑**：Markdown 可被外部编辑器改动；文件监测用于提示/调度，启动与周期校验补漏。单次 rename/写一半不能直接当成远端删除或稳定内容。
9. **旧版本兼容**：新对象 schema 不被旧客户端理解时暂停该类写入并提示升级，不忽略未知字段后回写删掉新数据。
10. **库切换与复制**：库身份与路径解耦；复制目录作为“同一库副本”还是“新库”必须显式选择。设备 ID 不随资料目录被盲目复制；迁移服务器不静默拼接两个云端库。

## 冲突规则

- **不同实体**：直接合并，如两台分别添加不同批注。
- **条目不同字段**：以共同基线做字段级三方合并；同一字段双方都改则保留冲突。
- **笔记同一正文**：可证明不重叠的修改才自动三方合并；其他情况保留本地、远端及基线，用户选择或人工合并。正文与 Source Link sidecar 作为一份逻辑文档校验，禁止留下悬空来源。
- **标签成员关系**：显式添加/移除操作，不能无条件取并集（会撤销用户移除）。
- **同一卡片、构思顺序**：首期实体级冲突；不同卡片可合并。不要以整份 state.json 的最后保存者覆盖所有构思。
- **删除与编辑并发**：提示保留修改副本/接受删除；不静默丢文。
- **PDF/解析结果**：二进制不文本合并，保留两个版本并选择活动版本；不同解析版本的译文、详略、批注不能直接混合。
- **译文/详略**：不同段落结果可合并；同一段的两份结果保留候选版本，用户修订不能被自动生成结果覆盖。
- **打开中的编辑器**：远端到达先判断 dirty；有未保存内容时保留草稿并提示外部更新，不自动 reload。暂停同步不暂停本地保存。

首期不引入实时协作 CRDT。多设备异步同步采用版本、三方合并及冲突副本即可形成可验证闭环；以后若需要多人同时编辑某个笔记，再限定该类正文评估 CRDT。

## Zotero 与 NeuInk 双系统的处理

保留两条独立链路：Zotero 自己负责其资料库同步；NeuInk 负责本产品的内容同步。

Zotero 接入适配器仍可读取本地源、提供导入和审阅回写。云端收到 NeuInk 笔记更新，不应自动向这台电脑上的 Zotero 回写。否则 A、B 两端加 Zotero 云形成环路，可能不断把 HTML/Markdown 转换视为新修改。

已联网的 Zotero 来源建议使用 provider + 云端 user/group library 标识 + item key；没有云身份的本地库由用户确认映射到一个 NeuInk 来源 ID。本机目录、localUserKey 和本地 libraryID 作为设备绑定信息，不能直接认为它们在另一台稳定等价。来源连接不可用时保留已同步的本地成果，重新绑定不重新导入整批条目。隐藏源条目不等于删除 Zotero 原始论文。

## 开源、自部署与隐私

- 无账号可用全部本地能力。账户只服务于同步；服务器不可达、服务停运或取消托管订阅，都不能阻止读取和导出已下载内容。
- 公布版本化协议、迁移规则和导出格式；客户端及服务端应可自行构建。官方云与自部署功能保持协议兼容。
- 官方托管成本集中在附件容量、流量、版本保留、备份和运维。可考虑元数据低成本托管、附件用户自备存储，但纯 WebDAV 不是自动解决元数据冲突的捷径。
- 初期不直接移植 Zotero 服务端代码。NeuInk 当前 Apache-2.0；上游的许可证应逐个核实，不能把 GPL/AGPL 源码复制后只补一句署名就当 Apache 自有实现。
- TLS、账户/库隔离、令牌吊销、设备管理、访问控制、请求幂等、备份恢复属于服务端必需品。附件 hash 去重限定账户或租户范围，不向其他用户泄露文件存在性。
- TLS 不等于端到端加密。若要求服务运营者也看不到内容，必须在协议冻结前决定：客户端加密、密钥恢复和轮换会影响合并、服务器搜索及网页阅读。建议独立评估后决定首版，不在没有实现时宣传零知识同步。
- 同步不能替代备份：同步会传播删除和错误。提供独立的历史版本和可验证的恢复流程。

## 分阶段实施与验收

### 第一阶段：本地数据准备（alpha）

盘点所有写入口和持久数据；拆设备设置/用户偏好/密钥；增加 library_id/device_id；记录事务和 outbox；定义实体及解析版本。用两份隔离的临时资料库和模拟远端做验证，不以用户日常库做破坏性测试。

验收：本地内容提交前后各崩溃点可恢复；外部修改不漏；纯打开/浏览/拖动视角不产生内容变更；同步关闭时原有本地流程保持可用。

### 第二阶段：最小同步闭环（alpha）

先实现条目、笔记、标签、独立批注，连通一个自部署服务，完成注册/登录或管理员配置账号、设备识别、版本条件写、增量拉取、离线队列、冲突处理和删除恢复。首期只面向同一用户多设备。

验收：两端离线分别改同一/不同对象，重连不丢内容；重复/乱序响应、超时、鉴权过期、磁盘满、损坏数据、版本不兼容时可恢复；一个对象失败不阻塞无依赖的其他对象。

### 第三阶段：完整阅读成果与附件（alpha 候选）

加入 PDF/笔记图片/解析资源、按需下载和断点恢复；加入逐段译文/详略与卡片构思；书签/阅读位置；将执行任务与成果分开。接现有全局通知/任务体系，明确“已保存到本地”“等待同步”“已同步”“存在冲突”“附件尚未下载”。

验收：新设备能显示重排版、译文、来源引用和卡片；没有安装或连接 Zotero 的设备也不丢已同步成果；大 PDF 不阻塞笔记；两端 AI 不会因同步结果重复扣费。

### 第四阶段：beta 稳定性

固定候选范围，真实双设备/弱网/长时间离线/旧客户端/数据迁移和备份恢复验证，完成原生 Tauri 编辑冲突与任务通知验收。只有用户确认稳定后晋级 main。团队协作、完整网页端和跨设备自动接管 AI 任务不混入此候选。

本次没有运行同步实验或原生 UI 验证，因为同步功能尚不存在；上述均为待实现的验收条件，不能计作已通过测试。
